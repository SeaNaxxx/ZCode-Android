# بروتوكول اختبار E2 على الجهاز الحقيقي — Vivo V2035 (Android 13, ARM64)

> القرار المُنفِّذ: E2 اختبار تحقق على ARM64، وليس اعتمادًا معماريًا نهائيًا.
> `dev` و`main` دون تعديل؛ كل العمل على الفرع التجريبي `e2/bionic-arm64-embedded`.
>
> **حدود الأدلة**: نتائج CI على محاكي x86_64 تُثبت منطق التطبيق فقط.
> الأسطر التي تحتها "غير مُثبت إلا على الهاتف" تبقى NOT TESTED حتى تنفيذ هذا البروتوكول.

## ما الذي يثبته هذا الاختبار (معايير السجل: ①②⑧ ثم ⑤⑥ ثم ⑦⑨)

| الاختبار | المعيار | ما يُثبته |
|---|---|---|
| T1 | ① | لا تنزيلات تشغيلية: أول تشغيل بلا إنترنت يكتمل من الأصول المضمّنة |
| T0/T2 | ② | معمارية الجهاز، إصدار Android، إصدار Node الفعلي، تحميل الوحدات الأصلية |
| T3 | ③ + ⑥ | حلقة الوكيل: إنشاء ملف/قراءته/تعديله + shell + Git داخل مساحة العمل |
| T4 | ⑤ + ⑧ | إعادة التشغيل: بقاء الملفات، إعادة استخدام البيئة دون إعادة تنزيل |
| T5 | ⑦ + ④ | المزوّد الحقيقي والمصادقة (اختبار مستقل، مفاتيح لا تُخزَّن في المستودع أو السجلات) |

قاعدة الفشل (شرطك رقم 6): **لا انتقال تلقائي إلى PRoot عند أي فشل.** كل فشل يُصنَّف:
1. عدم توافق ARM64/Bionic فعلي (مثل: فشل node-probe على الجهاز)
2. نقص في الملفات المضمّنة (مثل: asset ناقص، checksum داخلي خاطئ)
3. مشكلة صلاحيات Android (مثل: منع exec على Vivo)
4. خطأ في التطبيق (منطق Kotlin/UI)
5. اتصال/مصادقة (خارج معيار الـruntime المحلي)

## التجهيز

1. نزّل APK مباشرة من release **`e2-rc2`** (صفحة Releases في المستودع — ملفان
   منفصلان بدون zip: خذ **`zcode-e2-arm64-debug.apk`** فقط للهاتف).
   ⚠️ يجب أن يكون الإصدار **0.3.1-e2 (versionCode 4)** — نسخة إصلاح فشل
   `libz.so.1` (روابط soname صلبة). الإصدار الأقدم 0.3.0-e2 (code 3) فاشل
   على Vivo بسبب إنشاء symlink المرفوض على الجهاز.
2. ثبّته على الهاتف (تثبيت من مصادر غير معروفة مفعّل لهذا الملف).
3. لا حاجة لـ adb إطلاقًا؛ أوامر adb اختيارية للتأكيد الأعمق (قسم أخير).

## T0 — تسجيل معلومات الجهاز (معيار ②، قراءة أولى)

1. افتح التطبيق (قبل أي setup).
2. اضغط **Share diagnostics** → شارك النص إلى أي تطبيق ملاحظات/بريد واحفظه.
3. تحقق أن السطر يعرض: `device: vivo V2035 | Android 13 (SDK 33)` و `abis: arm64-v8a`
   و `embedded bionic bundle: true`.
4. ⚠️ الملف لا يتضمن أي مفاتيح أو إعدادات مزوّد — هذا مقصود.

## T1 — أول تشغيل بلا إنترنت (معيار ① — الحاسم)

1. **قبل أول تشغيل للبيئة**: فعّل وضع الطيران (Airplane mode) كاملًا.
   (التطبيق قد يكون مثبتًا ومفتوحًا؛ المهم ألا تبدأ "Set up local runtime" والإنترنت واصل).
2. اضغط **Set up local runtime**.
3. النتيجة المطلوبة: الوصول إلى **Ready** خلال دقائق، من الملفات المضمّنة حصرًا.
   النص المتوقع أثناء التقدم: verifying embedded Bionic bundle → extracting →
   checking Node.js on this device → Ready.
4. الأدلة: لقطة شاشة لحالة Ready + تصدير diagnostics (يظهر فيه `marker:` بـ
   `mode=bionic` و`nodeProbe=` إصدار node الفعلي على الهاتف + `bundleSha256`).
5. تفسير الفشل: أي فشل هنا بوضع الطيران = محاولة تنزيل فعلية أو asset ناقص
   (تصنيف 1 أو 2) — أرسل diagnostics فورًا ولا تعد المحاولة.

## T2 — تشغيل خادم ZCode الرسمي محليًا (معيار ③-التمهيد)

1. اضغط **Start ZCode** → انتظر **Running — http://127.0.0.1:3030**.
   ملاحظة: مع البدء يعمل أيضًا مزوّد الـmock المحلي (:9999) تلقائيًا — هذا مقصود
   لاختبار حلقة الوكيل دون إنترنت ودون مفتاح.
2. اضغط **Open ZCode** → يجب أن تفتح واجهة ZCode الرسمية (web) في التطبيق.
3. الأدلة: لقطة شاشة لواجهة ZCode داخل التطبيق.

## T3 — حلقة الوكيل الحقيقية (معيار ③ + ⑥ آلياتها)

المزوّد الافتراضي المضمّن هو mock مُبرمَج ينفّذ التسلسل: Write → Bash → Bash(git).

1. داخل واجهة ZCode، أنشئ جلسة جديدة وأرسل أي رسالة (مثلاً "ابدأ").
2. انتظر حتى تكتمل الجولة برسالة تحتوي `E1-MOCK-DONE`.
3. انقل شاشة الجولة (tool calls: Write / Bash / نتائجها) — لقطة شاشة.
4. **التحقق المستقل عن رسائل التطبيق**: ارجع لشاشة الحالة واضغط **Share diagnostics**
   — سطر `workspace files:` يجب أن يعرض (من نظام الملفات مباشرة):
   `hello.txt`, `bash-marker.txt`, و`.git` (دليل مستودع git حقيقي).
5. تحقق adb (اختياري، أقوى):
   ```bash
   adb shell run-as com.example.zcode_mobile sh /data/local/tmp/e2-run.sh cat files/workspace/hello.txt
   # المتوقع: E1 mock write: hello from Bionic
   adb shell run-as com.example.zcode_mobile sh /data/local/tmp/e2-run.sh sh -c "cd files/workspace && git log --oneline"
   # المتوقع: E1-MOCK-COMMIT
   ```
6. حدود الادعاء: نجاح T3 بـmock يثبت آليات حلقة الوكيل (أدوات حقيقية على ملفات حقيقية)
   ولا يثبت المصادقة أو الاتصال بمزوّد حقيقي — ذلك T5.

## T4 — الاستمرارية والاسترداد (معيار ⑤ + ⑧)

1. إغلاق التطبيق من مدير المهام بالكامل (Swipe away / Force stop).
2. أعد فتحه: يجب أن تظهر **Ready** مباشرة (وليس "Setup required").
3. اضغط Start ZCode → Running → Open ZCode.
4. **Share diagnostics** → قارن مع تصدير T3:
   - `marker:` نفس `provisionedAt` (لم تحدث إعادة تهيئة)
   - `workspace files:` نفس الملفات (hello.txt/bash-marker.txt/.git باقية)
5. وأنت في Running: فعّل وضع الطيران مرة أخرى — التطبيق والخادم المحليان يعملان
   بلا انهيار (انقطاع الشبكة لا يجب أن يُسقط الـruntime؛ فشل طلب مزوّد يظهر كخطأ
   في الجلسة لا كانهيار تطبيق).

## T5 — المزوّد الحقيقي (معيار ⑦ + ④ — بعد اجتياز T1–T4)

1. أوقف وضع الطيران، اتأكد من إنترنت عامل.
2. داخل واجهة ZCode: إعدادات المزوّد/الموديل → اختر مسارك الحقيقي
   (Connect to Z.ai Global / BigModel CN / Use API key) وأدخل بياناتك داخل التطبيق.
3. شغّل مهمة صغيرة حقيقية، مثلاً: «اقرأ hello.txt واذكر محتواه».
4. استجابة من موديل حقيقي = مصادقة واتصال سليمان.
5. خطوط حمراء: **لا تلتقط شاشة تحتوي مفتاح API**، ولا تشارك diagnostics أثناء
   وجود مفتاح في أي حقل إدخال مرئي. تصدير diagnostics لا يتضمن إعدادات المزوّد أصلًا.
6. فشل 429/[1113] (رصيد/حد استخدام) = المصادقة تعمل والفشل في الفوترة —
   يُسجَّل كما هو ولا يُحسب فشل runtime محلي.

## ما الذي يبقى NOT TESTED حتى تنفيذ هذا البروتوكول

- تشغيل Bionic node على ARM64 حقيقي (CI ثبّت x86_64 فقط)
- exec من ملفات التطبيق على Vivo (Funtouch) تحديدًا
- سلوك البطارية/إدارة العمليات في vivo مع الخدمة الأمامية
- استقرار WebView مع واجهة ZCode على Funtouch

## ما الجديد في rc2 (0.3.1-e2) وكيف تقرأ السجل

- روابط soname الحرجة (libz.so.1، libicuuc.so.78، ...) تُشحن الآن كملفات
  حقيقية (hard links) — لا يعود الـlinker يعتمد على إنشاء symlinks.
- إذا رفض الجهاز إنشاء symlinks سترى الآن السبب الحقيقي:
  `symlink FAILED: <name> (<Exception>: <message>)` (أول 3) ثم سطر إجمالي —
  انسخه كما هو في التقرير؛ يحدد التصنيف (3) بدقة.
- إذا نقص ملف حرج رغم ذلك: `bionic runtime incomplete on device: missing
  usr/lib/<name>` قبل أي خطأ linker غامض.
- فشل node-probe مع `CANNOT LINK` = ملف مضمّن مفقود على الجهاز (تصنيف 2/3) —
  ليس حكمًا على Bionic.
